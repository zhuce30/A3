# A3 数字人、导师人格与多智能体角色深度研究

> 项目：智学引擎 A3  
> 研究日期：2026-07-25  
> 研究范围：`OpenMAIC` 多角色 Agent、A3 面对面辅导数字人、A3 AI 课堂、实时语音链路、后端 QA Agent 及持久化边界  
> 文档性质：开发前审计、方案设计与实施状态记录

## 0. 实施状态（2026-07-25）

统一导师人格的 P0、P1、P2 核心链路已在本地功能分支 `codex/unified-tutor-persona` 完成，当前尚未推送 GitHub，也尚未部署到服务器。

- 已提供 `structured-teacher`、`socratic-guide`、`practice-coach`、`foundation-coach` 四种受控辅导方式。
- 用户偏好写入 `LearnerProfile.extra_profile.tutorPreference`，会话快照写入 `CoachingSession.metadata.tutorPersona`。
- A3 文本问答、面对面实时会话和 A3 AI 课堂均使用服务端白名单解析后的导师人格；SafetyAgent、RetrieverAgent、VerifierAgent 仍为强制步骤。
- OpenAI realtime 和 DashScope realtime 均从已认证的辅导会话解析指令和音色，浏览器不能提交任意系统提示词或 provider voice。
- 面对面辅导和 A3 AI 课堂共用同一导师偏好选择器；人格切换不会创建第二个 WebGL Canvas。
- 四种导师人格目前全部复用唯一的 `teacher-default-v1`（现有 `teacher.vrm`）视觉资产。它们改变教学策略和语音映射，不代表存在四套数字人模型。
- P3 多套授权视觉资产、P4 管理分析与效果评估仍是后续工作。

本文第 3、4 节保留开发前问题背景，并补充当前修复结果；第 9 节记录各阶段完成情况。

## 1. 结论先行

对当前仓库的代码、资产、接口和测试进行核对后，可以得出六个明确结论。

1. **OpenMAIC 的角色选择不能单独称为完整数字人。** 目前它主要是多智能体人设、静态 2D 头像和按 Agent 绑定的 TTS 语音，具备“角色化交互”，但没有 3D/2D 骨骼角色渲染、实时口型和行为状态同步。
2. **A3 面对面辅导已经具备真实的浏览器端 3D 数字人表现层。** 它使用 Three.js、VRM、VRMA 动作、表情、眨眼、口型和音频能量驱动，不依赖服务器 GPU，不是静态演示图。
3. **面对面辅导在开发前只有一个固定数字助教；当前已实现真实的导师人格切换。** 前端只提交 `personaId`，服务端从白名单解析教学策略和音色，普通问答与实时会话使用同一份会话人格快照。
4. **A3 自有 AI 课堂和生成后的 OpenMAIC 课堂必须分开描述。** `/a3/classroom` 是 A3 学习闭环页面；通过 `classroomUrl` 打开的 OpenMAIC 课堂才具备 AgentBar 和圆桌多角色。不能笼统说“AI 课堂完全没有角色”。
5. **不应直接把 OpenMAIC AgentBar 复制到 A3 页面。** 如果选择结果没有进入后端提示词、实时会话、TTS 和会话记录，用户看到的只是换名字或换头像，教学行为不会变化，属于伪角色选择。
6. **推荐方向是统一“导师人格”，而不是同时堆叠多套重型数字人。** 先让教学策略、语音和后端行为真正变化，再逐步增加经过授权的 VRM 外观。A3 课堂使用紧凑型导师入口，面对面辅导保留全屏数字人，圆桌讨论继续使用多 Agent。

## 2. 需要先区分的四个概念

当前讨论容易把“Agent”“角色”“声音”和“数字人”混为一谈。后续设计必须将它们拆成四层。

| 层级 | 解决的问题 | A3/OpenMAIC 当前实例 | 是否等于数字人 |
|---|---|---|---|
| Agent 能力 | 谁负责检索、验证、讲解、测评 | `RetrieverAgent`、`TeacherAgent`、`VerifierAgent` | 否 |
| 导师人格 | 老师如何教、如何提问、如何组织反馈 | 结构讲解、启发追问、例题实战、基础补强 | 否 |
| 语音身份 | 用什么音色、语速和停顿方式说话 | OpenMAIC per-agent TTS、实时 provider voice | 否 |
| 视觉化身 | 角色长什么样、如何动、是否口型同步 | A3 `teacher.vrm` + VRMA + viseme | 是数字人表现层的一部分 |

本项目中建议采用以下产品定义：

> **数字导师 = 经过约束的导师人格 + 学习工作流 Agent + 语音身份 + 可同步的视觉化身。**

仅有静态头像和 TTS，可以称为“角色化 Agent”或“语音角色”，不应在答辩中描述为完整数字人。仅有会动的 VRM，但所有角色都用同一提示词，也只是数字人外壳，不是个性化数字导师。

### 3.2 A3 面对面辅导已经具备什么

关键实现：

- `OpenMAIC/components/a3/features/coaching/digital-human-avatar.tsx`
- `OpenMAIC/components/a3/features/coaching/digital-human-three-stage.tsx`
- `OpenMAIC/components/a3/features/coaching/realtime-coaching-call.tsx`
- `OpenMAIC/components/a3/features/coaching/use-realtime-coaching.ts`

已经实现的能力：

- `idle`、`connecting`、`listening`、`thinking`、`speaking`、`visual_focus`、`degraded`、`error`、`ended` 状态。
- `aa`、`ih`、`ou`、`ee`、`oh` 五类口型表达。

### 3.3 OpenMAIC AgentBar 实际是什么

关键实现：

- `OpenMAIC/components/agent/agent-bar.tsx`
- `OpenMAIC/lib/orchestration/registry/store.ts`
- `OpenMAIC/lib/constants/agent-defaults.ts`
- `OpenMAIC/components/roundtable/index.tsx`
- `OpenMAIC/lib/hooks/use-discussion-tts.ts`

它支持：

- 老师、助教、好奇学生、思考者、记录员等预设或生成 Agent。
- 每个 Agent 拥有 `name`、`role`、`persona`、静态头像和颜色。
- 每个 Agent 可单独设置 TTS provider、model 和 voice。
- 多 Agent 圆桌讨论、轮流发言、讲台和白板动作权限。
- 生成课堂的 `stage.agentIds` 保存到 IndexedDB；服务器生成课堂也能将 Agent 配置写入 stage 并在浏览器恢复。

这套能力适合“多角色课堂”或“多观点讨论”，但缺少动画角色渲染和嘴型同步，所以不应直接包装为完整数字人。

### 3.4 A3 AI 课堂中的三类 Agent 不是三位老师

`backend/apps/learning/services.py` 的 `_classroom_agents()` 当前返回：

- 主讲教师 Agent：结构化讲解。
- 知识检索 Agent：本地知识库溯源。
- 练习诊断 Agent：错题与测评分析。

后端 QA 工作流实际由以下 Agent 串联：

```text
SafetyAgent
-> RetrieverAgent
-> TeacherAgent
-> VerifierAgent
-> FollowUpAgent
```

这些是内部能力分工，不是用户可以选择的导师人格。尤其是 `RetrieverAgent` 和 `VerifierAgent` 不应该被做成可选老师，否则用户可能误以为选择某个角色后就不再检索或验证。安全、检索和验证应始终存在于底层工作流。

## 4. 开发前缺口与当前修复

### 4.1 普通问答人格注入（已修复）

当前链路：

```text
面对面辅导/课堂文本提问
-> OpenMAIC /api/a3/coaching/respond
-> Django /api/v1/qa/interact/?q=...
-> run_qa_workflow()
-> TeacherAgent.run()
-> generate_tutoring_answer(question, target, sources)
```

开发前请求没有 `personaId`，`TeacherAgent` 始终使用同一套教学方式。当前 A3 代理会将选中的 `personaId` 转换为 Django 的 `persona_id`，Django 只接受白名单 ID，并把服务端解析后的教学策略注入 `TeacherAgent`。响应只返回公开的 `resolvedPersona`，不会返回私有 instruction 或 provider voice。

### 4.2 实时会话人格和语音绑定（已修复）

当前 `/api/a3/coaching/realtime/session` 请求体包含受控人格 ID：

```json
{
  "mode": "voice_video",
  "personaId": "foundation-coach"
}
```

当前实现会先在 Django 中保存会话人格快照，再创建 realtime provider 会话。OpenAI SDP 从已认证的 `coachingSessionId` 获取快照并写入受控 instructions 和 voice；DashScope 连接 URL 只携带会话 ID，proxy 使用登录 cookie 获取用户拥有的 Django 会话后再发送 `session.update`。未知或缺失的人格会降级为 `structured-teacher`，浏览器传入的任意 prompt 或 voice 不会被信任。

### 4.3 视觉状态和导师身份（按首期边界完成）

数字人状态继续由实时连接、倾听、思考、音频播放和视觉分析信号驱动。首期四种人格的公开快照均绑定 `avatarAssetId = teacher-default-v1`，因此切换人格只更新教学策略和语音映射，不卸载或重新加载 VRM，也不会创建多个 Canvas。多视觉资产属于 P3，不在本期伪装实现。

### 4.4 持久化边界（已修复）

- A3 全局导师偏好保存在 `LearnerProfile.extra_profile.tutorPreference`，刷新页面或更换设备后可从 Django 恢复。
- 每次辅导会话的公开人格快照保存在 `CoachingSession.metadata.tutorPersona`，避免目录后续变化改写历史会话语义。
- 已包含用户消息的会话切换人格时会结束旧会话并创建新会话，防止同一段对话前后人格不一致。
- OpenMAIC 圆桌内部 Agent 选择仍保持独立，不冒充 A3 用户的默认导师偏好。

## 5. 三种建设路线对比

### 路线 A：直接复用 AgentBar，只做前端角色选择

优点：

- 开发速度快。
- 能立即显示多个角色头像和名称。

问题：

- 普通问答和实时会话仍使用同一提示词。
- 角色选择无法影响安全、RAG、讲解策略和反馈方式。
- A3 与 OpenMAIC 的角色状态仍然分裂。
- 容易在答辩中被追问“选择角色后到底有什么实质变化”。

**结论：不采用。** 它只能制造 UI 完成度，不能形成可验证的产品能力。

### 路线 B：统一导师人格，先复用一套 VRM

做法：

- 建立 A3 统一 `TutorPersona` 契约。
- 用户选择的是“辅导方式”，不是虚假的多套数字人外观。
- `personaId` 同时进入普通 QA、实时会话、TTS 和会话记录。
- 第一阶段复用当前 `teacher.vrm`，通过名称、教学策略、音色和细微动作区分。
- A3 课堂、面对面辅导和 OpenMAIC 单导师模式共享同一人格定义。

优点：

- 教学行为可验证，符合学习软件定位。
- 不增加多套 16 MB VRM 的首期资产和性能成本。
- 不改变 Retriever、Verifier、Safety 等底层 Agent 边界。
- 后续可平滑增加多套授权 VRM。

**结论：推荐采用。**

### 路线 C：多套 VRM 或照片级数字人

可选技术包括多 VRM、Live2D、Wav2Lip/MuseTalk 类口型驱动、云端照片级数字人服务等。

问题：

- 多 VRM 增加下载体积、显存占用、WebGL 资源切换和授权管理成本。
- 自建照片级数字人通常需要 GPU 推理，不适合当前无独立 GPU 的 VPS。
- 云服务引入费用、延迟、隐私、可用性和供应商锁定。
- 先做外观不会改善 RAG、验证和教学质量。

**结论：作为第三阶段增强，不作为当前主线。**

## 6. 推荐的统一架构

### 6.1 领域模型必须拆分

```ts
type TutorPersona = {
  id: string;
  name: string;
  shortDescription: string;
  teachingStyle: 'structured' | 'socratic' | 'practice' | 'foundation';
  instructionPolicyId: string;
  avatarAssetId: string;
  voiceProfileId: string;
  allowedWorkflows: Array<'coaching' | 'classroom' | 'roundtable'>;
  enabled: boolean;
  schemaVersion: 'a3.tutor-persona.v1';
};

type AvatarAsset = {
  id: string;
  modelUrl: string;
  idleAnimationUrl: string;
  waitAnimationUrl: string;
  explainAnimationUrl: string;
  nodAnimationUrl: string;
  licenseId: string;
  performanceTier: 'standard' | 'light';
};

type VoiceProfile = {
  id: string;
  providerVoices: {
    openai?: string;
    dashscope?: string;
    browser?: string;
  };
  rate: number;
  pitch: number;
};
```

关键原则：

- 客户端只提交 `personaId`，不能提交任意 `systemInstruction`、voice 或模型路径。
- 后端从白名单目录解析人格，避免提示词注入和越权配置。
- 安全、检索和引用验证规则优先级高于人格规则，人格不得关闭 SafetyAgent、RetrieverAgent 或 VerifierAgent。
- 会话开始时保存人格快照，后续即使管理员修改人格目录，旧会话仍能解释当时采用了什么策略。

### 6.2 首期导师人格建议

| 人格 | 适用学生 | 教学行为 | 不应改变的底线 |
|---|---|---|---|
| 结构讲解 | 希望快速形成知识框架 | 先结论、再结构、后例子和练习 | 必须引用证据、不得编造 |
| 启发追问 | 已有基础但理解不牢 | 先问关键问题，逐步给提示，不直接泄露完整答案 | 安全与事实验证不降级 |
| 例题实战 | 需要通过操作和题目掌握 | 例题、步骤、检查点、变式练习 | 不替学生完成作弊型任务 |
| 基础补强 | 基础薄弱或术语负担高 | 少术语、短句、类比、一次一个概念 | 不牺牲准确性和来源 |

建议将界面文案写成“选择辅导方式”，不要在只有一套 VRM 时写“选择数字人形象”。系统可以根据画像推荐默认方式，但必须允许学生手动覆盖。

### 6.3 数据归属

第一阶段不必立即新建复杂的后台管理表，可以采用：

- 代码内置、版本化的导师人格目录。
- `LearnerProfile.extra_profile.tutorPreference` 保存用户默认人格。
- `CoachingSession.metadata.tutorPersona` 保存本次会话的人格快照、voice profile、schema version 和来源。

建议快照结构：

```json
{
  "tutorPersona": {
    "id": "foundation-coach",
    "name": "基础补强",
    "teachingStyle": "foundation",
    "instructionPolicyId": "a3.tutor.foundation.v1",
    "avatarAssetId": "teacher-default-v1",
    "voiceProfileId": "calm-teacher-v1",
    "schemaVersion": "a3.tutor-persona.v1"
  }
}
```

只有当管理员需要在线新增、停用和审计导师人格时，再升级为独立 `TutorPersona`、`VoiceProfile`、`AvatarAsset` 和 `UserTutorPreference` 表。

### 6.4 普通问答数据流

```text
学生选择辅导方式
-> 前端只发送 personaId
-> Django 校验 personaId 和允许使用的 workflow
-> 保存/读取用户导师偏好
-> QA payload 写入 resolvedTutorPersona
-> SafetyAgent
-> RetrieverAgent
-> TeacherAgent 使用受控人格策略生成答案
-> VerifierAgent
-> FollowUpAgent
-> 响应返回 personaSnapshot + traceId
```

提示词层级应固定为：

```text
平台安全和真实性规则
> A3 共同教学规则
> 受控导师人格策略
> 当前学习目标和画像摘要
> 知识库证据
> 学生问题
```

不能把前端传来的自然语言人格描述直接拼入 system prompt。

### 6.5 实时会话数据流

```text
POST /api/a3/coaching/realtime/session { mode, personaId }
-> Django/Next 解析白名单人格
-> CoachingSession.metadata 保存人格快照
-> realtime provider 获取 resolved instructions + provider voice
-> OpenAI SDP session 或 DashScope session.update 写入指令和音色
-> 返回 resolvedPersona 给前端
-> 数字人绑定 avatarAssetId，语音绑定 voiceProfileId
```

DashScope WebSocket proxy 不应直接信任浏览器传入的 prompt 或 voice。建议连接时携带 `coachingSessionId`，proxy 使用登录 cookie 向 Django 获取该会话的受控 runtime config，再生成 `session.update`。这样一套人格可以同时约束普通问答和实时语音。

OpenAI realtime 的 session config 需要真正写入 instructions 和解析后的 voice，不能只在接口响应里返回策略版本。

### 6.6 OpenMAIC 课堂协同

OpenMAIC 需要保留两种不同模式：

1. **单导师讲解**：从 A3 传入一个受控 `TutorPersona`，映射为主讲 Agent 的 persona 和 voice。
2. **圆桌讨论**：继续使用多个 Agent，各自拥有 persona 和 TTS；这是一种多观点学习活动，不要求同时渲染多个全尺寸 VRM。

`stage.agentIds` 继续负责课堂内部参与者，不替代 A3 用户的默认导师偏好。A3 生成 OpenMAIC 课堂时，应将所选导师快照放入生成请求或 handoff metadata，保证跨页面一致。

## 7. 页面应如何呈现

### 7.1 面对面辅导

推荐：在进入实时通话前提供一个紧凑的“本次辅导方式”选择区，默认使用画像推荐结果。

每项只展示：

- 名称。
- 一句话教学方式。
- 试听按钮。
- “适合你”的推荐标记。

选择后进入现有全屏数字人界面。切换辅导方式不重新创建 WebGL Canvas，不重复加载 VRM，只更新受控人格、语音和必要的动作倾向。进行中的会话不允许无提示切换，避免同一会话前后人格不一致。

### 7.2 A3 AI 课堂

建议增加同一套“导师模式”入口，但不要让数字人长期占据课件主体区域。

- 课件、引用和任务仍然是主内容。
- 导师以可折叠的紧凑陪伴区或“进入面对面辅导”入口存在。
- 提问时使用当前选中的导师人格。
- 需要摄像头、屏幕分析或沉浸对话时进入面对面辅导。

不建议把 580 至 760 像素高的现有数字人舞台直接复制到课堂阅读页面，这会压缩课件空间并造成双重主任务。

### 7.3 OpenMAIC 圆桌

继续保留静态头像和 TTS。多个全尺寸 VRM 同时渲染会增加浏览器 GPU/内存压力，并显著增加谁在说话、动作同步、音频打断和资源释放的复杂度，当前没有必要。

## 8. 性能与部署判断

### 8.1 服务器是否需要 GPU

当前 VRM 数字人在学生浏览器中通过 WebGL 渲染，服务器只提供静态模型文件、业务接口、实时代理和模型 API 转发。因此当前海外 VPS 没有独立 GPU，并不妨碍 VRM 数字人运行。

服务器主要压力来自：

- Django 请求和知识库检索。
- realtime proxy 长连接。
- 外部 ASR/LLM/TTS provider 延迟。
- 视频、知识库解析等 Celery 任务。

增加导师人格本身不会显著增加服务器计算量，主要增加少量配置解析、会话 metadata 和不同 voice 的 provider 调用。

### 8.2 浏览器性能策略

现有懒加载、可见性暂停和遮挡暂停应继续保留，并补充以下约束：

- 同一页面只保留一个 WebGL renderer 和一个 VRM 实例。
- 人格切换优先复用现有 VRM，不卸载再加载同一模型。
- VRM、VRMA 设置长缓存并使用内容哈希或版本号更新。
- 限制 device pixel ratio，建议上限 1.5；低性能设备使用 20 至 24 FPS 或静态 fallback。
- 页面隐藏、数字人不在视口或被屏幕共享主视图覆盖时停止动画循环。
- 组件卸载时释放 geometry、material、texture、AnimationMixer、AudioContext 和 object URL。
- 多套 VRM 只能按需加载当前一套，不能一次预载全部角色。
- 移动端默认使用轻量画质，不能因为人格选择导致布局和 Canvas 反复重建。

### 8.3 为什么暂不采用照片级自建数字人

MuseTalk、Wav2Lip 一类方案更适合视频生成或服务端推理，通常需要 GPU 才能获得可接受的实时帧率。把它们部署到当前无独立 GPU 的 VPS，会与 Django、Celery、知识库和视频任务争抢 CPU、内存和磁盘，反而增加 502 和服务中断风险。

如果以后确实需要照片级效果，应使用独立 GPU 服务或成熟云 API，并通过异步/流式接口与 A3 解耦，不能放入主 Web 后端进程。

## 11. 验收标准

### 功能真实性

- 同一问题选择不同导师人格时，回答结构符合各自受控策略，但事实、引用和安全结论保持一致。
- `personaId` 确实进入 Django QA workflow 和 realtime provider session，不只存在于前端状态。
- 未知人格、禁用人格和跨 workflow 人格被后端拒绝。
- SafetyAgent、RetrieverAgent、VerifierAgent 不因人格切换而被绕过。
- 辅导会话详情能显示当时使用的人格快照和实际 voice/provider。
- 用户刷新页面或更换设备后，默认辅导方式仍可恢复。

### 实时数字人

- provider 输出 viseme 时优先使用 provider cue；没有 cue 时使用音频能量 fallback。
- 切换人格不会重复创建 WebGL Canvas 或重新下载同一 VRM。
- 页面离开视口、标签页隐藏和数字人被主预览覆盖时暂停渲染。
- VRM 或 WebGL 失败时仍可完成语音/文本辅导，并明确显示降级状态。

### A3 与 OpenMAIC 边界

- A3 课堂中的导师选择影响 A3 后端 QA。
- OpenMAIC 圆桌的多 Agent 仍能独立选择和发言。
- 页面不把 `RetrieverAgent`、`VerifierAgent` 等内部能力 Agent 伪装成可选数字老师。
- OpenMAIC 课堂 handoff 能追溯主讲导师，但不覆盖课堂自己的参与者列表。

### 性能

- 首屏不请求 `teacher.vrm`，只有进入或接近数字人视口时才加载。
- 单页面最多一个活动 VRM renderer。
- 桌面端和移动端 Canvas 均非空且没有明显布局遮挡。
- 当前 VPS 无 GPU 时，普通后端服务不承担数字人逐帧渲染或口型推理。

## 13. 最终产品定位

建议将三种交互模式明确分工：

```text
AI 课堂
-> 课件、知识库证据和任务优先
-> 一个选定导师人格
-> 数字人仅作为可折叠陪伴或进入面对面辅导的入口

面对面辅导
-> 一个选定导师人格
-> 全屏 VRM 数字人
-> 实时语音、摄像头/屏幕分析、RAG 和会话总结

圆桌讨论
-> 多个角色 Agent
-> 静态头像 + 独立 TTS
-> 多观点、辩论、协作和课堂活动
```

这套分工不会把三种页面做成重复功能，也符合当前工程和服务器条件。A3 的竞争力不应是“角色数量多”，而应是：**导师表现层真实、教学人格可控、回答有知识库证据、行为能回写学习闭环，并且每次会话都可追溯。**

## 14. 本次研究的直接回答

1. **OpenMAIC 可以选择不同角色回答，这是不是数字人？** 不是完整数字人。它是多角色 Agent、静态头像和 TTS 的组合。
2. **面对面辅导是否缺少这一部分？** 是。它有真实 VRM 数字人，但缺少导师人格选择和后端行为绑定。
3. **AI 课堂是否也要加？** 应该共享同一导师人格，但采用紧凑入口，不应复制全屏数字人舞台长期占据课件区域。
4. **是否现在就做多套数字人模型？** 不建议。先用一套 VRM 打通真实人格、提示词、语音、持久化和会话审计，再增加授权外观。
5. **服务器没有 GPU 是否能做？** 当前浏览器 VRM 路线可以，不需要服务器 GPU。照片级服务端实时数字人暂不适合当前 VPS。
